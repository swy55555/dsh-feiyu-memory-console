# D 阶段 · 自动注入对照评估协议（冻结版）

> 目的：只回答一个问题——**自动注入跨模块记忆，是否让回复更好**。
> 结论只作用于“自动注入”这一项；A–C 的来源追溯、trace、只读关联不因 D 失败而回滚。

---

## 1. 样本与冻结

- 样本文件：`state/eval-sample.json`（`scripts/build-eval-sample.mjs` 生成）。
- 规模：30 条 owner 私聊 episode，按“该轮之前是否有跨日同话题记忆”分层：
  - `cross-day` 15 条；
  - `fresh` 15 条；
  - `low-confidence` 当前池为 0（现有数据里没有可稳定识别的冲突/低置信聊天样本），报告需注明这一层缺失。
- **时间边界**：每条记录 `memoryBoundaryAt`；注入组只能使用 `at < memoryBoundaryAt` 的记忆，禁止把该轮及其之后的信息喂给模型。
- 记忆快照：两组共用同一份 `taste.json`、`self-memory.json`、`continuity.json`、`narrative` 版本；快照在评估开始前复制并冻结。

## 2. 两组只差一个变量

| 项 | 基线组 | 注入组 |
|---|---|---|
| 模型 / 参数 / 提示词模板 | 相同 | 相同 |
| 记忆快照 | 相同 | 相同 |
| 跨模块注入（taste / self-memory / 关联） | 关 | 开 |
| 叙事注入 / 节律 / 目标 | 保持现状 | 保持现状 |

- 同一段输入各跑一次，输出打乱顺序；
- 评分者不知道哪条属于哪组（盲评）；
- 不触发真实 QQ 消息：用固定样本直接调用模型，不经过唤醒链路。

## 3. 指标与分母（先定义，后统计）

| 指标 | 分母 | 分子 |
|---|---|---|
| 重复提问率 | 样本中**旧记忆里确有答案**的轮次（预标 `hasAnswerInMemory`） | 回复追问该信息、且旧记忆已包含答案的轮次 |
| 正确连续性 | 同上 | 回复准确引用具体旧事实（时间/事件/偏好），人工判定为“是” |
| 错误引用率（主） | 全部回复数 | 含至少一次错误记忆断言的回复数 |
| 错误断言率（辅，仅诊断） | 记忆断言总数 | 与来源不符的断言数 |
| token 增量 | 基线组实际输入 token 均值 | 注入组均值 − 基线均值 |
| 预算丢弃率 | 注入组总轮次 | trace 中 `dropped.reason=budget` 的轮次 |

- 错误引用**主指标固定为回复级**（分子 ≤ 分母，不会超过 100%）；断言级只作辅助诊断，不参与保留判定；
- 所有“人工判定”由同一人完成，判定标准写在评分表里；
- 连续性只有“正确接上具体旧事实”算，模糊的“感觉更连贯”不计。

## 4.2 三类样本分开判

| 集合 | 判定内容 | 指标 |
|---|---|---|
| `effect`（gateHit 且有答案） | 是否避免重复提问、是否接上旧事实 | 重复提问率、正确连续性、错误引用率、token |
| `personalization`（gateHit 但无答案） | 兴趣是否被恰当使用 | 盲评：相关且准确使用 / 生硬提及 / 误用；不计入重复提问率 |
| `control`（未命中） | 门槛是否合理拦住 | 只报告 gateHit 情况，不与有效注入样本混算 |

- `personalization` 的盲评规则：只问“这条回复里对兴趣的使用是否**相关且准确**”，贴在无关话题上算误用，硬塞算生硬；
- 三个集合样本量分别报告，不合并成一个大分母。

## 4.3 版本与保存

- 每次新增真实命中样本，生成新版本 fixture（`eval-fixture-v2.json`、`v3`…），**不覆盖**旧版本；
- 评分表只含随机 pair ID 与匿名 A/B 回复（`docs/eval/eval-score-sheet-v<版本>.md`）；
- 条件映射与回复正文放本机 `~/.dsh/eval/`，不进插件发布文件；
- 当前 22 条全部被门槛拦住，只能作为 control 集，不能当效果样本。

## 4. 保留门槛（写死）

自动注入只有在**同时满足**以下三条时保留：

1. 重复提问率相对下降 **≥ 20%**，或正确连续性相对提升 **≥ 15%**；
2. 错误引用率 **不高于**基线（≤ 基线）；
3. 输入 token 增量 **≤ +15%**。

任一条不满足：**关闭自动注入**，保留 A–C 的来源追溯、trace 和只读关联。

## 5. 报告边界

- 30 条是配对试点，只能给方向性结论，不能宣称普遍效果；
- `low-confidence` 层缺失，需在报告中明确；
- 不把“更连贯”当成主要证据，主要看可数的行为指标和错误引用。

## 4.1 零基线特例

如果基线组的重复提问率或正确连续性为 **0**，“相对改善 20% / 15%”没有定义：

- 该项视为**不满足**；
- 除非另一项有效指标达到门槛，且错误引用率不增加、token 增量 ≤ +15%；
- 否则不保留自动注入。

## 6. 两组样本，分开报告

| 样本 | 文件 | 用途 |
|---|---|---|
| 覆盖率基线 | `docs/eval/eval-sample.json`（30 条，跨日分层） | 说明“当前系统有多少轮会真正注入”；**不作效果结论** |
| 实际可注入集 | `docs/eval/eval-injectable.json` | 含三个标签；effect / personalization / control 三组分开 |

- 两个标签分开：`injected`（装配器实际注入）与 `hasAnswerInMemory`（记忆里是否有可支撑答案）**不是一回事**；
- 报告必须分别给出：覆盖轮次占比、实际注入样本数、其中有答案的样本数；
- 不为凑数量放宽时间边界。

## 7. 预检口径说明

- 预检不发起网络请求，但会**写本地报告** docs/eval/eval-preflight.json；它不是严格只读。

- `hasAnswerInMemory` 是保守判定：只统计“该轮之前、同话题且字面重合 ≥ 阈值”的记忆，宁可少算；
- 因此重复提问率与正确连续性的**分母是 14，不是 30**；报告必须用 14 作分母；
- 预检不调用模型、不触发桥接或 QQ 唤醒。
